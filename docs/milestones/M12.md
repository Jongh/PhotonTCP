# M12 — v1.0 사인오프 실측: APK 실빌드 + 실기 광학 링크

## 목표

이 마일스톤이 끝나면 **"설치하고 실행하면 됨"이 실제 수치로 바뀐다**. 폰에 APK가 설치돼 앱이
뜨고, 체크 A(셀프체크 수신율)와 체크 B(폰+PC 2-머신 왕복)가 실측되어 v1.0 게이트의 통과 여부가
숫자로 결정된다. 통과하면 다음 릴리즈가 v1.0.0이고, 막히면 **어디서 왜 막혔는지가 재현 가능한
형태로** 남는다.

동시에 **하드웨어·툴체인 없이 지금 당장 닫을 수 있는 것은 전부 닫는다** — 빌드 사전조건 점검의
자동화, 데스크톱 Kivy에서의 앱 선검증, M11이 이월한 사소 2건, 그리고 v0.11.0 릴리즈로 드러난
문서의 버전 복제 제거. 그래서 하드웨어가 또 미뤄지더라도 이 사이클은 빈손으로 끝나지 않는다.

## 배경

### 왜 지금인가

- **v1.0 수동 사인오프 실측이 4사이클 연속 이월**(M8·M9·M10·M11-review). 회고
  (`docs/reports/retro.md`) 최상단 표에서 유일한 `미결` 행이고 **최우선**으로 표시돼 있다.
  막고 있는 것은 코드가 아니라 **장비**였고, M11이 그 장비(폰)를 쓸 수 있는 코드 경로를 만들었다.
- **M11-impl 후속 메모 1(최우선)**: *"APK 실빌드가 미수행이다. 이 사이클은 스펙·문서·앱·어댑터까지
  갖췄고 남은 것은 실행이다."* 다음 사이클 첫 항목으로 ① `camerax_provider` clone ② Docker Desktop
  기동 또는 WSL2 일반 배포판 설치 ③ `buildozer android debug` ④ 실패 시 `android.ndk` 조정 또는
  opencv 우회를 지목했다.
- **M11-review(2회차) 「다음 단계」**가 같은 순서를 다시 확인했고, 실기 첫 확인 항목으로
  `flip_vertical`/`flip_horizontal`·`colorfmt`에 더해 **wakelock 실동작**과 **camera4kivy의 버퍼
  재사용 여부**를 지목했다.

### 이번 사이클이 안고 있는 불확실성 (숨기지 않고 적는다)

1. **툴체인 비용**: M11-T06은 사용자 판단으로 실빌드를 돌리지 않았다 — 수 GB 다운로드 + opencv
   소스 컴파일을 포함해 최초 빌드가 30~90분 이상이고, Docker 데몬이 정지 상태이며 WSL2에 일반
   배포판이 없다. **이 비용을 치를지는 impl 착수 시점의 사용자 판단**이며, 이 마일스톤은 그
   판단이 어느 쪽이든 깨지지 않도록 설계한다(완료 기준 7~10의 폴백 규정).
2. **opencv p4a 레시피**: M11이 "이 이식의 최대 불확실성"으로 명시했다(p4a 이슈 #3203 — opencv
   4.5.1 레시피 × numpy 2.3.0). 실패 시 우회는 `docs/mobile-build.md` 5-3에 이미 문서화돼 있으나,
   우회하면 `decode_frame`이 항상 `None`이라 **광학 링크 자체가 성립하지 않는다**. 그래서 우회는
   "앱이 뜨는지"까지만 확인하는 경로이고 사인오프 경로가 아니다.
3. **실기 부재 항목**: camera4kivy 콜백 시그니처·RGBA 행 순서·분석 버퍼 재사용, Android GLES의
   `luminance` 텍스처 수용, `flip_*` 기본값, wakelock 실동작. **T02가 이 중 상당수를 데스크톱에서
   앞당겨 확인**하도록 설계한 이유가 이것이다 — 폰에서 처음 만나면 원인 분리가 어렵다.

### v0.11.0 릴리즈가 드러낸 것

M11-T08이 **코드**의 버전 선언처를 `pyproject.toml` 하나로 통일했는데, **문서 두 곳이 여전히 값을
복제**하고 있어 이번 릴리즈로 즉시 낡았다 — `docs/conventions.md:61`의 *"현재 버전: `0.10.0`"* 과
`docs/project-context.md:10`의 *"현재 `0.10.0`"*. tide 규약 자체가 *"드리프트 차단은 갱신 단계
추가가 아니라 **복제 제거**로 해결된다"* 고 적고 있으므로, 갱신이 아니라 제거로 닫는다(T04).

### 회고 후속 항목과의 관계

이 마일스톤이 집는 것은 최상단 `미결` 행 **v1.0 수동 사인오프 실측**(T05~T09)과 `미반영` 행
**실 열화(저조도·모션블러) 수신율 실측 기록**(T09에 포함)이다. `미반영`으로 남아 있는 세 행
(Micro-QR 원천 제거, `__version__` 불일치, `docs/v1.0-signoff.md` 미커밋)은 **M11에서 이미
닫혔고 v0.11.0에 실렸다** — 표의 상태만 밀려 있으므로 `/tide:retro`가 `반영`으로 옮길 몫이지
이 마일스톤의 태스크가 아니다(규약상 회고 표는 `/tide:retro`만 쓴다). 나머지 `미반영` 행
(`max_retx` 노출, 데이터 실패 push 이벤트화, latency/jitter, half-close·다중 파일, FEC)은
이번 범위가 아니다.

### 이번 사이클이 닫는 단위 / 이후로 이월하는 단위

**이번 사이클 (M12)**

1. 빌드 사전조건 점검의 자동화 (다음 시도를 값싸게 만든다)
2. 데스크톱 Kivy 선검증 (실기에서 만날 항목을 앞당겨 분리)
3. M11 이월 사소 2건 + 문서 버전 복제 제거
4. APK 실빌드 → 폰 설치 → 체크 A·체크 B 실측 → 사인오프 기록 (폴백 규정 아래)

**이후로 이월 (이번 범위 아님 — 명시)**

- **대체 디코더 백엔드의 실제 구현**(ZXing via pyjnius 등). opencv 레시피가 실기에서 실패하는
  것이 **확인된 뒤에야** 정당화된다 — M11이 자리만 만들어 두었고 그 판단 근거가 T05에서 나온다.
- 앱 UX(설정 영속화·로그 뷰·파일 전송 UI), iOS, 서명·스토어 배포, 해상도/프레임율 튜닝.
- `unregister_decoder_backend()`/`registered_decoder_backends()` 짝 API,
  `run_peer(should_stop=…)` 취소 훅. 둘 다 M11-review가 구조적 후속으로 분류했고 사인오프를
  막지 않는다.

## 태스크 상세

### M12-T01: 빌드 사전조건 점검 하니스

- **변경 파일**: `examples/mobile_build_preflight.py`(추가), `docs/mobile-build.md`(수정)
- M11-T06이 **손으로** 확인한 툴체인 상태 점검을 스크립트로 고정한다. `examples/`에 두는 것은
  `optical_selfcheck.py`의 선례를 따르는 것이다(하드웨어/환경을 묻는 수동 하니스의 자리).
- 점검 항목(각각 OK/BLOCK/WARN + 사유 한 줄):
  - **툴체인**: `docker` 존재와 **데몬 응답**(`docker info`), `wsl -l -v`의 일반 배포판 유무,
    `java`, `adb`, `buildozer`, `gradle`. Docker 경로와 WSL2 경로 중 **적어도 하나가 성립**하면
    OK로 본다(둘 다 없으면 BLOCK).
  - **저장소 사전조건**: 레포 루트의 `main.py` 존재, `camerax_provider/` 디렉터리 존재
    (`.gitignore` 처리 대상이라 빌드 환경마다 clone 필요 — 없으면 BLOCK + clone 명령 안내).
  - **스펙 정합**: `buildozer.spec`을 `configparser`로 파싱해 필수 키 존재
    (`package.name`·`package.domain`·`source.dir`·`requirements`·`android.permissions`·
    `android.archs`·`android.api`·`p4a.hook`)를 확인하고, **`version.regex`를 실제로 적용해**
    `pyproject.toml`에서 버전이 추출되는지 실측한다(M11-impl 이슈 3이 이 정규식에서 한 번
    물렸으므로 회귀 지점이다).
  - **디스크 여유**: 최초 빌드가 수 GB를 쓰므로 임계값(예: 20GB) 미만이면 WARN.
- 출력은 사람이 읽는 표 + **exit code**(BLOCK 있으면 1, 아니면 0). `--json` 옵션은 두지 않는다
  (소비자가 없다 — 필요해지면 그때 연다).
- **엣지**: 도구 부재와 도구 실패(예: docker 있으나 데몬 정지)를 **구분해서** 보고한다 — M11-T06의
  실측이 정확히 그 구분이었고, 대처가 다르다. 하위 프로세스 호출은 전부 타임아웃을 두고, 어떤
  점검이 예외로 죽어도 나머지 점검은 계속한다(하니스가 첫 실패에서 멈추면 준비 목록으로 못 쓴다).
- `docs/mobile-build.md` 0절에 "빌드 전에 이 스크립트를 돌려라" 한 줄과 사용법을 더한다.

### M12-T02: 데스크톱 Kivy 선검증 + `app.py` 상태 전이 테스트

- **변경 파일**: `tests/test_mobile_app.py`(추가), `photontcp/mobile/app.py`(수정 — 결함이 드러난
  경우에 한함), `README.md`(수정)
- **목적**: M11이 "실기에서 처음 만나는 것"으로 남긴 항목 중 **기기 없이 확인 가능한 것**을
  앞당긴다. 폰에서 처음 만나면 빌드·기기·코드 중 어디가 원인인지 분리하기 어렵다.
- **① 데스크톱 실행**: `pip install kivy`(또는 `pip install -e .[mobile]`) 후
  `python -m photontcp.mobile.app`을 띄워 **위젯 트리가 그려지는지**, 설정 행·QR 영역·상태 줄·
  버튼이 배치되는지, Start를 눌렀을 때 카메라 부재/`camera4kivy` 부재가 **크래시 없이 상태 줄
  메시지로** 끝나는지 확인한다. 결과(스크린샷 또는 상태 줄 문자열)를 impl 보고서에 기록한다.
  - **`colorfmt="luminance"` 텍스처 수용 여부**를 데스크톱 GL 백엔드에서 먼저 본다. 거부되면
    `KivyDisplay(..., colorfmt="rgb")` 한 줄 교체가 대안임이 이미 문서화돼 있다. 데스크톱 결과가
    Android GLES를 보장하지는 않지만, **거부가 나오면 그 자체로 유용한 신호**다.
  - 데스크톱에 웹캠이 있으면 `camera4kivy`의 데스크톱 프로바이더로 **실제 캡처까지** 시도한다.
    되면 `flip_vertical`/`flip_horizontal` 기본값과 RGBA 행 순서를 기기 없이 실측할 수 있다.
    **폴백**: Kivy·camera4kivy 설치가 이 환경에서 실패하거나 카메라가 없으면, 어느 단계에서 왜
    막혔는지를 기록하고 ②로 넘어간다 — 이 태스크는 그것으로 완료된 것으로 본다.
- **② 상태 전이 테스트**: Kivy 설치 여부와 무관하게 도는 부분을 테스트로 고정한다. Kivy가 없으면
  `tests/test_mobile_devices.py`의 선례대로 **최소 스텁을 `sys.modules`에 심어 실제 `app.py`를
  로드**해서 검증한다(스텁을 검사하지 않는다).
  - `PhotonTCPApp.format_summary()`가 `PeerResult`를 요약 줄로 정확히 렌더하는지(순수 정적 함수).
  - `_read_settings()`가 잘못된 입력(빈 문자열·`"abc"`·`"0"`·음수)에서 기본값 또는 `MIN_HOLD`로
    떨어지는지 — **`hold`가 절대 `run_peer`가 거부하는 값이 되지 않는다**를 단언한다
    (M11-review 권장 4의 UI 쪽 절반이 아직 테스트로 고정돼 있지 않다).
  - `on_event()`가 `EVENT_KINDS` 전 종류에서 예외 없이 상태 문자열을 만드는지, 알 수 없는 kind를
    조용히 무시하는지.
  - `_make_preview()`가 `camera4kivy` 부재에서 `(None, 사유 문자열)`을 돌려주는지.
- **엣지**: `app.py`는 `kivy.app.App`을 상속하므로 스텁 `App`이 필요하다. `Clock.schedule_once`
  스텁은 **동기 실행**으로 두어 마샬링 경로가 테스트에서 관찰 가능하게 한다.

### M12-T03: M11 이월 사소 2건

- **변경 파일**: `photontcp/qr/decode.py`, `photontcp/optical/__init__.py`,
  `tests/test_decode_backend.py`, `tests/test_optical_import.py`(추가)
- **① cv2 부재 시 실패 import 반복**(M11-review 1회차 사소 8): 실패한 import는 `sys.modules`에
  캐시되지 않아 `decode_frame` 호출마다 `sys.path` 전수 탐색이 일어난다. 그런데 그 상태가 바로
  `docs/mobile-build.md` 5-3이 권하는 **opencv 제거 우회 경로의 상시 조건**이라 비용이 문서가
  권하는 경로 위에 얹힌다.
  - **제약(이것이 설계의 핵심이다)**: M11-T01은 가용성을 **일부러** 캐시하지 않았다 —
    `active_decoder_backend()`가 stale `"cv2"`를 보고하지 않게 하기 위함이고, 기존 테스트
    `test_cv2_backend_returns_after_block_is_lifted`가 **"막았다 풀면 회복된다"** 를 단언한다.
    따라서 캐시를 넣더라도 **그 성질이 유지돼야** 한다.
  - **정해둔 경로**: 실패(부재)만 캐시하고, 캐시를 무효화하는 **명시적 지점**을 둔다 —
    `register_decoder_backend()`·`set_decoder_backend()` 호출 시 무효화 + 공개
    `reset_decoder_backend_probe()` 제공. 기존 테스트가 통과하도록 fixture에서 그 함수를 부른다.
    이 경로가 기존 성질과 충돌한다고 판단되면 **캐시를 넣지 않고 "왜 넣지 않았는지"를 기록**하는
    것도 유효한 완료다(완료 기준 3이 그렇게 쓰였다).
- **② `photontcp.optical`의 eager import**(사소 11): `optical/__init__.py`가 `.peer`를 무조건
  import하고 `peer.py`가 `photontcp.app`·`photontcp.session`을 import하므로,
  `import photontcp.optical`만으로 상위 계층이 전부 끌려온다 — README가 말하는 "상위 계층이
  `Channel`에만 의존한다"의 **반대 방향** 의존이 전송 계층 패키지 초기화에 들어와 있다.
  - **정해둔 경로**: 모듈 수준 `__getattr__`(PEP 562)로 `run_peer`·`PeerResult`를 **지연
    재수출**한다. `__all__`은 그대로 두어 공개 표면이 바뀌지 않게 하고, `from photontcp.optical
