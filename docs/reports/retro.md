# tide 회고 (retro)

> 누적 마일스톤·보고서를 가로질러 본 회고. 회고 시점마다 이 문서 **최상단에** 새 섹션을
> 쌓는다(기존 섹션 보존). `/tide:retro`가 생성·갱신하는 읽기 전용 산출물.

## 2026-09-08 (v0.10.0 시점) — 3차 회고: M8~M10 (실물 광학 채널 + 하드닝 + QR 디코드 견고화)

### 집계 범위

- 마일스톤 **M8~M10** 3건, 보고서 **6건**(impl 3 + review 3), 릴리즈 **v0.8.0 → v0.10.0**.
- 2차 회고(v0.7.0 시점, M1~M7) 이후 구간. 그 이전 이력은 하단 과거 섹션이 보존한다.
- 테스트 추이: 172(M8) → 175(M9) → 188(M10) passed, 전 구간 회귀 0.

### 반복된 문제·이슈 군집

- **실 하드웨어 검증 부재 — 3사이클 연속 이월** (등장: M8-review 권장1, M9-review 권장3,
  M10-review 잔여리스크 a) — "빛만으로 실 통신"이라는 프로젝트의 목적 그 자체가 매 사이클
  *다음으로* 밀렸다. 처리 추이: M8 = 미배선(캡처 인메모리) → M9 = **하니스는 완성**
  (`optical_selfcheck.py`, `--real --role`, v1.0 게이트 기준 문서화) → M10 = 디코드율 상한만 올림.
  **남은 것은 코드가 아니라 실측 한 번**이다(카메라·화면 2대). 세 리뷰가 모두 "수동 사인오프
  필수"로 정직하게 고지했고 릴리즈를 막지 않기로 일관되게 판정했으나, 후속으로서는 **한 발도
  움직이지 않은 유일한 항목**이다.
- **cv2 디코드 취약성이 상류 설계를 막은 연쇄** (등장: M9-T03, M9-review 권장1·2, M10 전체) —
  M9에서 2바이트 nonce가 cv2 `QRCodeDetector`의 **콘텐츠 의존 블라인드스폿**에 걸려 세션 통합
  테스트를 결정적으로 깨뜨렸고, 그 때문에 완료 기준 문구(다중 바이트 nonce)를 포기하고 윈도우
  dedup으로 우회했다. M10이 전처리 캐스케이드 + 대체 detector 폴백으로 디코드를 견고화하자 그
  제약이 사라져 nonce 2바이트가 **재검증 후 반영**됐다. 처리 추이: 우회(M9) → 원인 제거(M10) →
  보류 항목 회수(M10-T05). **하류(디코더) 한계가 상류(프레이밍) 설계를 규정한 사례**로, 다음에도
  "테스트가 특정 값에서만 깨진다"면 매체 계층을 먼저 의심할 근거가 된다.
- **타이밍 의존 테스트의 플레이키** (등장: M8-impl(데드라인 60s 상향), M9-impl(pacing 절대 임계
  flaky → 차등 단언), M10-T05(그 차등 단언이 다시 ~50% flaky → **단측 경계 2개**로 재작성)) —
  같은 테스트가 두 사이클에 걸쳐 두 번 고쳐졌다. 수렴점은 *"실시간 측정값끼리 비교하지 말고,
  `time.sleep`이 하한이라는 성질만 단측으로 단언한다"* 이다. 처리 추이: 튜닝 → 차등 → 단측 경계
  (M10에서 격리 10/10).
- **마일스톤 문구 ↔ 구현 메커니즘의 괴리, 그리고 리뷰의 과장 교정** (등장: M9-impl 후속1,
  M9-review 권장1) — impl이 *"윈도우만으로 래핑 거짓 dedup이 이미 제거"* 라고 적었고 리뷰가
  **"수학적으로 완전 제거는 아니다 — 실 제거는 윈도우가 아니라 ARQ 프로토콜 특성"** 으로 정정했다.
  판정을 뒤집진 않았으나 근거를 바로잡은 사례로, **집행력을 사실보다 넓게 주장하지 않는다**는
  규율(`vacuous-pass` 부류의 이웃)이 실제로 작동한 지점이다.
- **환경 의존 기능은 best-effort + 우아한 degrade로 수렴** (등장: M9-T01(`CAP_PROP_BUFFERSIZE`는
  백엔드가 무시 가능 → 드레인이 실질 안전망), M10-T02(WeChat/Aruco 부재 시 폴백 생략 = 캐스케이드
  단독), M8-T03(cv2 부재 시 `None` 재export)) — 세 사이클이 같은 형태를 반복해 채택했다:
  **가용성 probe → 없으면 조용히 축소, 계약은 불변.** 이 저장소의 굳어진 패턴으로 볼 만하다.

### 수용된 트레이드오프

- **nonce 1바이트 유지 (M9-T03)** — 2바이트가 cv2 디코드 회귀를 유발해 *일시* 수용했고,
  **M10에서 해소**됐다. 수용이 영구가 아니라 **차단 요인 제거 후 회수된** 드문 사례.
- **Micro-QR 경계 배제 (M10-impl 후속1 / M10-review 권장1)** — cv2가 Micro QR을 지원하지 않으나,
  본 프로토콜 패킷은 헤더만 22B(+nonce 2B)라 실사용에서 Micro 경계에 닿지 않아 비차단으로 수용.
  다만 리뷰가 **원인이 디코더가 아니라 인코더**(`segno.make(..., micro=True)` 기본값)임을 밝혀,
  `encode_frame(micro=False)` 한 줄로 원천 제거 가능함이 확인됐다 → 후속으로 남김.
- **열화 코퍼스의 큰 헤드룸 (M10-T04)** — 임계 0.85에 실측 1.00. 인메모리 열화는 의도적으로
  가볍고, 강한 실 열화(저조도·모션블러)는 셀프체크로만 측정 가능하다는 한계를 명시한 채 수용.
- **`_MAX_DRAIN=4` 고정 한도 (M9-T01)** — 무한 드레인의 과지연 위험 대신 유한 한도. 백엔드별
  효과 차이는 감수.
- **캐스케이드의 이론적 base64 거짓-성공 (M10-review 사소3)** — QR 자체 EC·포맷 정보 + 상위 CRC로
  실질 무해하고 M10 이전 단일패스도 동일 노출이라 신규 리스크가 아니다 → 기록만 하고 수용.
- **`_alt_decode`의 변형 재계산 (M10-review 사소4)** — 1차가 전 변형 실패한 **콜드패스 한정**이라
  핫패스 불변. 캐싱은 폴백이 잦은 환경이 생길 때 검토.
- **`OpticalChannel.pair(seed=…)` 무효 (M8-review 사소5)** — 인메모리 광학은 RNG가 없어 시드가
  무의미하나 loopback과의 **API 대칭**을 위해 인자를 남기고 docstring에 명시.

### 릴리즈 판정·버전 추이

- **M8**(실물 광학 채널): 판정 **가능** → **v0.8.0 (minor)** — `OpticalChannel`·`optical` 서브패키지·
  디바이스 추상 신규 공개 API 추가, 차단 0, 172 passed.
- **M9**(실물 링크 하드닝 + 검증 하니스): 판정 **가능** → **v0.9.0 (minor)** — 페이싱·드레인·가드·
  윈도우 dedup + 검증 하니스, 차단 0, 175 passed. **v1.0은 수동 사인오프 미수행으로 명시적 보류**.
- **M10**(QR 디코드 견고화): 판정 **가능** → **v0.10.0 (minor)** — 공개 시그니처·None 계약 불변인
  견고화 + nonce 2바이트, 차단 0, 188 passed.
- 추이 요약: **3사이클 연속 차단 0 · 판정 가능 · minor**. major(v1.0)만 세 번 모두 같은 이유로
  보류됐다 — 코드가 아니라 **실측**이 없어서.

### 회고 메모

1. **1순위는 코드가 아니라 30분짜리 실측이다.** v1.0 사인오프는 세 사이클 연속 표에 남았고, 그
   사이 하니스·문서·게이트 기준은 전부 갖춰졌다(`docs/v1.0-signoff.md`). 다음 사이클은 **새 기능
   마일스톤보다 이 실측을 먼저** 잡는 편이 프로젝트 목적에 직결된다. 실측이 PASS면 다음 릴리즈가
   곧 v1.0.0이고, FAIL이면 그 수치 자체가 다음 마일스톤(광학 튜닝)의 입력이 된다.
2. **2순위는 Micro-QR 원천 제거**(`encode_frame(micro=False)`) — 리뷰가 원인을 인코더로 특정했고
   변경이 한 줄 + 연동 테스트 조정이라 비용이 작다. 여기에 **버전 상수 불일치**
   (`__init__.py` 0.1.0 vs pyproject 0.10.0)와 **`docs/v1.0-signoff.md` 미커밋**을 같은 사이클의
   작은 태스크로 묶으면 잔여 정리가 한 번에 닫힌다.
3. **"수용"은 영구가 아니다.** M9의 nonce 1바이트 수용이 M10에서 회수된 것은, 수용 사유를
   *"현재 이것이 막고 있다"* 로 구체적으로 적어 뒀기 때문에 그 차단 요인이 사라진 순간 재검토가
   촉발된 결과다. 앞으로도 수용 항목은 **무엇이 막고 있는지**를 함께 적을 것.
4. **타이밍 테스트는 실측값끼리 비교하지 않는다.** 두 사이클을 소모한 뒤 얻은 규칙이다 —
   `time.sleep`이 하한이라는 **성질**만 단측으로 단언한다. 새 타이밍 테스트를 쓸 때 이 형태를 먼저
   고른다.
5. **이번 회고는 tide 구성 최신화(2026-09-08) 직후에 돌았다.** 그 변경(`.gitignore`,
   `docs/conventions.md`, `docs/project-context.md` 신규)과 본 회고의 편집은 **다음 impl 보고서의
   「변경 파일 요약」에 포함**해야 릴리즈 커버리지 체크가 "어떤 보고서도 설명하지 않는 변경"으로
   advisory를 내지 않는다.

### 반복된 문제·이슈 군집

- **"이월 → 정리 마일스톤" 사이클이 닫혔다** (등장: M3·M4·M5·M6 권장 → M7에서 해소) — 1차 회고가 제안한
  "흩어 넣지 말고 신뢰성 정리 마일스톤으로 묶어라"를 M7로 실행했고, 누적 권장 대부분이 한 번에 해소됨.
  **메타 교훈: 회고의 후속 추적이 실제로 다음 마일스톤 범위를 결정했다**(retro→milestone 피드백 루프가 작동).
- **통합 태스크가 상태머신 결함을 표면화 → 이후 사이클은 결함 0** (등장: M2·M3 결함 / M4·M5·M6·M7 무결함) —
  초기(M2 순차 종료, M3 최종 ACK 손실)엔 통합 태스크가 상태머신 결함을 드러냈으나, **M4 이후 4개 사이클
  연속 소스 결함 0건**. `Channel` 추상 + 순수 컴포넌트 + 동기 펌프 설계가 상위 계층을 무수정으로 얹게 해
  결함 유입을 구조적으로 막은 결과로 보인다.
- **스레드 안전성** (등장: M1·M5·M7) — M1 공유 RNG, M5 cv2 detector로 반복 등장하다 **M7에서 일괄 해소**
  (RNG 락 + 스레드로컬 detector). 단 검증은 "스모크" 수준 — **실제 동시성 정확성은 M6 실물 광학(카메라 스레드)
  에서 본격 검증**으로 이월(처리 추이: 코드 반영 완료, 정확성 검증 이월).
- **단일 프레임 용량/크기 한계** (등장: M3·M5·M6) — NACK 단일 seq, 단일 QR 용량, 파일 chunk_size. M7에서
  QR 용량 가드(`QRCapacityError`)·NACK 억제로 일부 정리. 대용량/스트리밍 전송의 흐름 제어는 여전히 이월.

### 수용된 트레이드오프

- **단일 스레드 동기 펌프 모델** (M2~M7 전반) — 결정적 테스트 우선. M7에서 스레드 안전성 코드는 깔되,

### 회고 메모

1. **최우선 미반영 후속 = 스레드 동시성 정확성 검증**, 그리고 그것이 곧 **6단계 실물 광학** 마일스톤의

2. **실물 광학은 결정적 자동 테스트가 어렵다**(하드웨어·대화형). 마일스톤 설계 시 "타이밍·프레임 버퍼링

3. **남은 미반영은 대부분 저우선/기능 확장**(arq max_retx 노출·실패 push·latency 채널·half-close·다중 파일·
   FEC). 다음 정리 마일스톤이 필요할 만큼 쌓이기 전까지는 기능(실물 광학) 진행이 합리적.
4. **검증된 패턴 유지**: ① 손실/통합 테스트 표준화, ② `Channel` 추상 위 순수 컴포넌트 + 동기 펌프(결함 유입
   차단), ③ 사전 확정 설계 질문(매 마일스톤 전), ④ 회고→정리 마일스톤 피드백 루프.
5. **1.0 후보**: 실물 광학(M6 단계)까지 완료해 "빛만으로 채팅·파일 실통신"이 실증되면 v1.0 선언 시점.

### 회고 메모

1. **최우선 미반영 후속 = flush-on-close (M4-review).** 파일 전송 마일스톤에서 "전송 완료 후 종료" 보장이 없으면 마지막 청크 유실 위험. 파일 전송 착수 시 **필수 반영**.
2. **M3 리뷰 권장 4건이 계속 이월 중**(NACK 억제·데이터 idle 타이머·재전송 상한/파라미터 노출·종료 이벤트 정합성). 다중 스트림·장기 전송에서 영향이 누적될 수 있어, 흩어 넣기보다 **"신뢰성 정리(hardening) 마일스톤"으로 묶어** 처리하는 편이 효율적.
3. **스레드 안전성(공유 RNG·cv2 detector)은 M6 실물 광학에서 카메라 스레드를 도입하는 시점에 일괄 해소**. 그 전엔 단일 스레드 모델이라 비용 대비 이득 없음 — 지금 손대지 말 것.
4. **통합/손실 시나리오 테스트를 일찍 두는 것이 효과적**이었다(M2·M3 상태머신 결함을 통합 태스크가 조기 발견). 새 마일스톤마다 "손실 채널 + 통합" 테스트를 표준으로 유지.
5. **단일 프레임 용량(QR) ↔ 파일 전송 청크 크기 설계가 맞물린다.** 파일 전송 마일스톤에서 `max_payload` 상한(QR 용량)과 청크/분할 전략을 함께 설계(M5 권장 1과 연계).
6. **버전 규율 정착**: 최초 릴리즈는 초기 버전 그대로, 이후 신규 계층마다 minor. 1.0 진입은 실물 광학(M6)·파일 전송까지 완료해 "절대적 매체 위 실 통신"이 증명된 시점이 자연스러운 후보.
