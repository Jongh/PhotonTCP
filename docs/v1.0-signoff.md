# v1.0 수동 사인오프 가이드 (실 하드웨어 체크)

## 이 문서는 무엇인가

PhotonTCP의 자동 테스트(수는 `python -m pytest -q`의 출력이 단일 출처다 — 사이클마다
변하는 값이라 여기 박지 않는다)는 모두 **인메모리**로 광학 채널을 검증한다 — QR
인코드/디코드와 프로토콜 로직은 증명하지만, 실제 **화면→카메라 광학 경로**(빛)는 CI에서
실행되지 않는다. v1.0("빛만으로 실 통신")은 그 마지막 한 칸을 **사람이 실 하드웨어로
증명**하는 것을 전제로 한다. 이 가이드는 그 수동 사인오프 절차다.

> **자동화 아님**: 아래 두 체크는 카메라·화면·조명·정렬이 필요해 CI로 돌릴 수 없다. 손으로
> 실행하고, 결과를 기록한 뒤, 통과하면 `v1.0.0`을 릴리즈한다.

**통과 기준 요약 (둘 다 충족해야 v1.0):**

| 체크 | 무엇 | PASS 기준 |
|---|---|---|
| A. 셀프체크 | 1대(반이중): 화면→자기 카메라 | 수신율 **≥ 80%** (exit 0 / `PASS`) |
| B. 2-머신 왕복 | 2대(전이중): 서로 마주봄 — PC+PC(2절) **또는 폰+PC(2-B절)** | 양쪽 **ESTABLISHED → MATCH → CLOSED** (`PASS`) |

## 0. 사전 준비

```bash
# 저장소 루트에서, 광학 의존성 설치
pip install segno opencv-python
# (권장) cv2 대체 detector로 회복력↑ — 디코드 견고화 폴백이 WeChat을 먼저 시도함
pip install opencv-contrib-python   # opencv-python 과 택일 설치 권장
```

- **카메라**: USB/폰 웹캠 또는 노트북 내장캠. 체크 B는 **2대**(각자 화면+카메라)가 필요.
- **화면**: QR을 띄울 모니터. 밝기 적당히, 화면 반사·직사광 피하기.
- 모든 명령은 **저장소 루트**에서 실행한다.
- 어느 detector가 활성인지 확인(수치 재현·비교에 기록):
  ```bash
  python -c "from photontcp.qr.decode import _resolve_alt_kind; print('alt detector:', _resolve_alt_kind())"
  ```
  `'wechat'` / `'aruco'` / `None`(폴백 없음) 중 하나가 나온다. 결과를 사인오프 기록에 적는다.

## 1. 체크 A — 셀프체크 (1대, 반이중)

한 대에서 화면에 QR을 띄우고 **그 화면을 자기 카메라로 잡아** 수신율을 측정한다. 광학
경로의 *물리*(카메라가 화면을 얼마나 잘 읽나)만 보는, 프로토콜 없는 최소 루프다.

### 실행

```bash
python examples/optical_selfcheck.py
```

그런 다음 **웹캠을 화면의 `PhotonTCP` 창에 겨눈다**(폰/USB캠을 모니터 향해 고정, 또는
내장캠을 둘째 모니터에 향하게). QR이 프레임 안에 꽉 차게, 고른 조명에서, 흔들리지 않게
유지한다. 자동으로 진행·종료되며 키 입력은 필요 없다.

### 결과 읽기

마지막에 다음과 같은 리포트가 출력된다:

```
Total 20 | hits 18 | misses 2 | mismatches 0
Receive rate (correct decodes): 90.0% (PASS threshold 80%)
PASS
```

- **`PASS` + 수신율 ≥ 80%** → 체크 A 통과 (프로세스 exit 0).
- **`FAIL`** (수신율 < 80%, exit 1) → 아래 튜닝 후 재시도.
- "No camera at index 0 ... skipping"(exit 0)는 **통과가 아님** — 카메라가 안 잡힌 것. 장치
  연결/인덱스를 고친다.

### 옵션 (기본값)

| 플래그 | 기본 | 의미 |
|---|---|---|
| `--camera N` | `0` | 카메라 장치 인덱스 |
| `--scale PX` | `6` | QR 모듈 픽셀 크기 — **클수록 디코드 쉬움** |
| `--hold SECS` | `0.3` | 프레임을 캡처 전 띄워두는 시간 |
| `--count N` | `20` | 보낼 고유 프레임 수 |
| `--window NAME` | `PhotonTCP` | 창 제목 |
| `--fullscreen` | off | 전체화면 표시 |

### 수신율이 낮을 때 (대개 코드가 아니라 광학 문제)

1. **`--scale` 올리기** — 가장 효과 큼. 예: `--scale 10` 또는 `--scale 12`.
   ```bash
   python examples/optical_selfcheck.py --scale 12 --hold 0.5
   ```
2. **`--hold` 올리기** — 카메라가 각 프레임을 잡을 시간 확보(특히 `mismatches`가 많으면).
3. **정렬·조명** — QR을 프레임 중앙에 꽉 차게, 초점 맞추고, 화면 반사 제거.
4. **`--fullscreen`** — 더 큰 물리 QR.
5. `mismatches`는 보통 *이전 프레임의 신선하지 않은 캡처*이지 손상이 아니다 — `--hold`를
   키우면 줄어든다.

목표: **튜닝된 리그에서 수신율 ≥ 80%**. 한 번 맞춘 `--scale`/`--hold`/조명 조합을 기록한다.

## 2. 체크 B — 2-머신 왕복 (전이중, 빛만으로 실 통신)

두 대를 **마주보게** 두고 각자 ONE 피어의 실 `OpticalChannel`(Cv2Display + Cv2Camera)을
구동한다. 핸드셰이크 → 작은 메시지 교환 → 정상 종료가 **모두 빛 위로** 오간다.

> **한 대로는 안 됨**: 한 화면+카메라는 자기 창을 볼 수 없다. 진짜 광학 루프는 **두 화면 +
> 두 카메라**가 필요하다. 각 피어의 `Cv2Display` 창이 **상대 피어 `Cv2Camera`의 시야** 안에
> 들어와야 한다.

### 물리 배치

```
   [머신 1 화면] ───빛──▶ [머신 2 카메라]
   [머신 1 카메라] ◀──빛─── [머신 2 화면]
```

- 두 화면을 서로(또는 상대 카메라) 향하게 배치. 두 QR 창이 각각 상대 카메라에 꽉 차게.
- 같은 `--scale`/`--hold`를 양쪽에 동일하게 준다(체크 A에서 맞춘 값 사용 권장).

### 실행 (두 프로세스)

```bash
# 머신 1 (연결 개시자)
python examples/optical_link.py --real --role sender   --scale 12 --hold 0.5

# 머신 2 (응답자)
python examples/optical_link.py --real --role receiver --scale 12 --hold 0.5
```

- `--camera N` 으로 캡처 장치 선택(기본 `0`).
- `--window NAME` 으로 창 제목 변경(겹침 방지에 유용).
- 두 프로세스를 거의 동시에 띄운다(개시자가 SYN을 먼저 화면에 표시 → 응답자가 캡처).

### 결과 읽기

각 프로세스 끝에 요약이 나온다:

```
Summary: REAL OpticalChannel role=sender | established=True | messages=MATCH | closed=True | wall=...s
result: PASS
```

**체크 B 통과 = 양쪽 프로세스 모두:**
- `established=True` (핸드셰이크 → **ESTABLISHED**),
- `messages=MATCH` (보낸 메시지가 빛 너머에서 그대로 복원),
- `closed=True` (정상 **CLOSED**),
- → `result: PASS`.

`FAIL`은 대개 상대 피어가 반대 role로, 이 화면/카메라를 마주보고 실행되지 않은 경우다(2-프로세스·2-머신 데모임을 기억).

## 2-B. 체크 B 변형 — **폰 + PC** 조합 (M11부터 가능)

체크 B는 "화면 2 + 카메라 2"를 요구하지만, **두 번째 PC가 없어도 된다**. M11에서 안드로이드
폰이 한 피어로 동작하게 되었으므로(`photontcp.mobile`의 Kivy 어댑터 + 앱), 폰 1대 + PC 1대로
같은 전이중 왕복을 돌릴 수 있다. 이 절은 그 조합의 절차이며, **위의 2-머신 PC 왕복 절차를
대체하지 않는다** — 둘 중 편한 쪽을 고르면 된다(둘 다 체크 B의 PASS 기준은 동일하다).

> **실측은 아직 수행되지 않았다 (다음 사이클 항목).** M11은 "장비가 없어서 못 함"을 "설치하고
> 실행하면 됨"으로 바꾸는 것까지가 범위였다(`docs/milestones/M11.md` — 실기 사인오프 실측은
> 명시적으로 이월). 아래 절차를 실제로 돌려 수치를 기록하는 일이 **다음 사이클의 첫 항목**이고,
> 그때까지 v1.0은 주장하지 않는다.

### 준비

1. APK를 빌드해 폰에 설치한다 — [`docs/mobile-build.md`](mobile-build.md)의 Docker 또는 WSL2
   경로, 그리고 `adb install` 절. PC 쪽은 기존과 같이 `pip install segno opencv-python`
   (권장: `opencv-contrib-python`).
2. **역할 배정**: PC를 `sender`(연결 개시자), 폰을 `receiver`로 두는 것을 권장한다. 개시자가
   먼저 SYN을 화면에 띄우므로, 재시작이 쉬운 쪽(PC 프로세스)이 개시자인 편이 다시 맞추기 쉽다.
   반대 배정도 성립한다 — **두 기기가 서로 다른 role**이기만 하면 된다.

### 물리 배치

```
   [PC 화면] ───빛──▶ [폰 후면 카메라]
   [PC 웹캠] ◀──빛─── [폰 화면]
```

- 폰을 스탠드/거치대에 고정해 **폰 화면이 PC 웹캠 시야에 꽉 차게**, 동시에 **폰 카메라가 PC
  화면의 QR 창을 정면으로** 보게 둔다. 손으로 들지 않는다(흔들림이 곧 미스다).
- 폰 후면 카메라를 쓰면 폰 화면과 카메라가 서로 반대편을 보므로, PC 화면과 PC 웹캠을 **같은
  방향**(웹캠을 모니터 위)에 두고 폰을 그 앞에 마주 세우는 배치가 가장 쉽다.

### 폰 쪽 실전 주의 (이 조합에서만 생기는 것들)

| 항목 | 조치 | 왜 |
|---|---|---|
| **화면 밝기** | **최대**로. 자동 밝기 끄기 | 폰 화면이 PC 웹캠에게는 광원이다. 대비가 곧 디코드율 |
| **화면 꺼짐 방지** | 앱이 `android.wakelock = True`로 빌드되므로 **기본 조치 불필요**. 그래도 꺼지면 화면 꺼짐 시간을 세션보다 길게(또는 개발자 옵션의 "충전 중 화면 켜짐") | 세션 중 화면이 꺼지면 표시 피어가 그대로 죽는다. `buildozer.spec`이 wakelock + `WAKE_LOCK` 권한을 켜 두었으나 **실기 미검증**이라 폴백을 함께 적는다 |
| **자동 회전 잠금** | 세로 고정으로 잠근다 | 앱은 `orientation = portrait`이지만, 거치대에서 기기를 돌리면 정렬이 깨진다 |
| **카메라 선택** | 앱 설정의 `camera`를 **`back`**(후면) 권장 | 후면이 화질·초점이 낫다. `front`(전면)는 프리뷰가 좌우 반전이라 앱이 `flip_horizontal`로 보정한다 — 그 보정은 **미검증**이다 |
| **`scale` / `hold`** | **양쪽을 같은 값으로** 맞춘다. 체크 A에서 튜닝한 값(예: `--scale 12 --hold 0.5`)을 그대로 | 표시 페이싱이 어긋나면 상대 카메라가 프레임을 통째로 놓친다 |
| **야간 모드/블루라이트 필터** | 끈다 | 색온도 변화가 대비를 깎는다 |
| **절전 모드** | 끈다 | 프레임율·밝기를 낮춰 캡처를 놓친다 |

폰 화면은 물리적으로 작으므로 **`scale`을 PC보다 더 키워야 할 수도 있다**. 다만 QR이 화면 밖으로
잘리면 아예 디코드가 안 되므로, 잘리지 않는 최대값이 상한이다.

### 실행

```bash
# PC 쪽 (기존 CLI 그대로 — 계약은 M10과 동일)
python examples/optical_link.py --real --role sender --scale 12 --hold 0.5
```

폰 쪽은 설치한 PhotonTCP 앱을 열고 상단 설정 줄에서:

- `role` = **`receiver`** (PC가 `sender`일 때. 반대면 반대로)
- `scale` = PC와 **같은 값** (예: `12`)
- `hold` = PC와 **같은 값** (예: `0.5`)
- `camera` = `back`

를 고른 뒤 **Start**를 누른다. 최초 실행에서 안드로이드 **카메라 권한**을 묻는다 — 허용해야
한다(거부하면 앱은 크래시하지 않고 상태 줄에 사유를 띄운 채 멈춘다). 두 쪽을 거의 동시에
시작한다(개시자가 SYN을 먼저 띄우고 응답자가 그것을 잡는다).

### 결과 읽기

PC 쪽은 기존과 동일한 요약 줄이 나온다:

```
Summary: REAL OpticalChannel role=sender | established=True | messages=MATCH | closed=True | wall=...s
result: PASS
```

폰 쪽은 같은 값이 앱 하단 요약에 표시된다(`established / MATCH / closed / PASS·FAIL`) — 두 front-end가
같은 `run_peer` 구동 루프와 같은 `PeerResult`를 쓰기 때문이다.

**통과 기준은 체크 B와 동일**하다: **양쪽 모두** `established=True` · `messages=MATCH` ·
`closed=True` → `PASS`.

### 이 조합에서 잘 나오는 실패

| 증상 | 원인 | 조치 |
|---|---|---|
| 폰이 한 프레임도 못 읽음(핸드셰이크 무진행) | APK에서 **opencv가 빠졌다** | `python -c "from photontcp.qr.decode import active_decoder_backend as a; print(a())"`가 PC에서 `cv2`인 것과 달리, 폰 앱에서는 디코더가 없으면 수신이 0이다. `docs/mobile-build.md` 5-3 참조 |
| 폰이 한 프레임도 못 읽음(opencv는 들어 있음) | 캡처 프레임의 **상하/좌우 반전**(camera4kivy 행 순서 미검증) | `KivyCamera`의 `flip_vertical` / `flip_horizontal`을 뒤집어 재빌드 |
| 폰 화면에 QR이 안 뜸 | GLES 백엔드가 `luminance` 텍스처를 거부 | `KivyDisplay(colorfmt="rgb")`로 바꿔 재빌드 |
| 중간에 링크가 끊김 | 폰 화면 꺼짐 / 절전 진입 | 화면 꺼짐 시간·절전 설정 위 표대로 |
| 한쪽만 PASS | role 중복(둘 다 sender) 또는 정렬·타이밍 | role을 서로 다르게, 두 화면을 상대 카메라 시야에 맞추고 동시 재시작 |

기록할 것은 2-머신 PC 왕복과 같다(아래 3절) — 여기에 **폰 모델·안드로이드 버전·APK가 opencv를
포함했는지**를 덧붙인다.

## 3. 결과 기록 & v1.0 릴리즈

### 현재 사인오프 상태 (M12 시점)

> **v1.0.0 후보가 아니다** — 체크 A·체크 B 모두 **미수행**이고 실측값이 존재하지 않는다.
>
> **막은 것은 하드웨어가 아니다.** M12 시점에 안드로이드 실기는 사용 가능한 상태였고, 폰+PC
> 체크 B 절차(아래 2-B)도 갖춰져 있다. 막은 것은 **APK가 나오지 않은 것** 하나다 —
> M12-T05가 실빌드를 끝까지 돌려 원인을 p4a 상류 버그 한 지점으로 특정했다
> (`docs/mobile-build.md` 5-4절). opencv를 포함한 모든 네이티브 레시피는 그 지점 **전에**
> 이미 성공적으로 컴파일된다.
>
> **v1.0까지 남은 것 셋**:
> 1. p4a의 안드로이드 휠 URL 버그 우회 (상류 수정 · 리비전 고정 · p4a 포크 중 하나)
> 2. APK 산출 + 폰 설치, 그리고 기동 스모크 6항목 확정
>    (권한 · `luminance` 텍스처 · `flip_*` · 콜백 시그니처 · 버퍼 재사용 · wakelock)
> 3. 체크 A(수신율 ≥ 80%) · 체크 B(양쪽 PASS) 실측
>
> 이 상태는 M12까지 **5사이클 연속 이월**이지만 성격이 바뀌었다 — M8~M11은 *"두 번째 기기가
> 없어서"* 였고, M12는 *"기기는 있는데 빌드가 막혀서"* 다. 병목이 하드웨어에서 툴체인으로
> 옮겨 갔고, 그 병목은 원인이 특정된 단일 지점이다.
>
> **데스크톱에서 앞당겨 확정된 것 둘**(M12-T02, 위 목록 2의 일부를 미리 닫은 것):
> `colorfmt="luminance"` 텍스처가 데스크톱 GL 백엔드에서 수용되고,
> `connect_camera(enable_analyze_pixels=True, camera_id=…)` 키워드가 camera4kivy 0.3.3에서
> 그대로 받아들여진다. **안드로이드 GLES와 실제 픽셀 콜백은 여전히 미검증**이다(웹캠 부재).

두 체크가 모두 PASS면 **회고/릴리즈 노트에 다음을 기록**한다(재현성):

- 날짜, 하드웨어(카메라 모델·해상도, 화면), 조명 조건
- 활성 대체 detector (`wechat`/`aruco`/`None`)
- 사용한 `--scale`/`--hold` 값
- 체크 A 수신율(%), 체크 B 양쪽 요약 줄(established/MATCH/closed)

그런 다음:

```
/tide:release v1.0.0
```

(릴리즈 절차는 `release` 모드로 진행 — CHANGELOG에 위 사인오프 수치를 함께 적는다.)

## 부록 — 빠른 트러블슈팅

| 증상 | 가능 원인 | 조치 |
|---|---|---|
| `No camera at index 0` / exit 0인데 캡처 없음 | 카메라 미연결/인덱스 불일치/타 앱 점유 | `--camera 1` 등 인덱스 변경, 타 카메라 앱 종료 |
| 수신율 낮음(MISS 다수) | QR 작음·초점·조명 | `--scale`↑, 초점·정렬, 반사 제거 |
| `mismatches` 다수 | 직전 프레임의 stale 캡처 | `--hold`↑ |
| `This example requires segno and opencv-python` | 의존성 미설치 | `pip install segno opencv-python` |
| 체크 B가 한쪽만 PASS | 정렬/타이밍 불일치 | 두 창을 상대 카메라 시야에 정렬, 동시에 재시작, 동일 `--scale`/`--hold` |
| 디코드 회복력이 약함 | 코어 opencv-python(대체 detector 없음) | `pip install opencv-contrib-python` (WeChat 폴백 활성화) |

> 참고: cv2 `QRCodeDetector`의 콘텐츠 의존 블라인드스폿은 M10의 전처리 캐스케이드 + 대체
> detector 폴백으로 대부분 회복된다(`python examples/qr_decode_bench.py`로 인메모리 디코드율
> 확인 가능). 실 수신율은 결국 광학(조명·초점·정렬)에 가장 크게 좌우된다.
